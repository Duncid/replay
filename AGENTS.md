# Project Rules

- Composer lives on tune_assets; a database trigger extracts credited MusicXML creators for every insert, publishers preserve existing credits when metadata is missing, and the worker reads original XML before exported XML because conversion can replace credits with software placeholders.
- The upload form reads original XML or the MXL container's score in the browser; confirmed metadata is stored with build jobs and overrides worker credits, so edits survive conversion and retries without waiting for a worker deployment.

- Local tune publishing awaits asset loading and combines instrument-only exports for tunes, nuggets, and assemblies while preserving track IDs; grouped exports remain authoritative so publishing matches local playback.

- `ios-learn-native/` is a standalone Swift/SwiftUI iPad app (Learn mode only), separate from the Capacitor wrapper in `ios/` — keep the two native projects independent; the native app talks to the same Lovable Cloud edge functions and shares no code with the web app.
- Native note highway (`ios-learn-native/ReplayLearn/Highway/`): drawing (SpriteKit scene), timing (HighwayClock) and scoring (HitJudge) stay separate, and all nodes/effects are pooled up-front — keeps frame rate steady and scoring testable.
- The web student entry uses `TuneLibrary` and the existing `TuneMode`, without teacher selection calls; progression resolution stays in a pure utility because curriculum node keys can differ from published music references.
- Native student entry reads published tune assets and account-owned profile acquisitions directly, then uses tune-coach/tune-evaluate with the pooled highway; pure Swift progression tests stay outside the app target so they can run without Apple UI frameworks.
- Web Quest and Tune Manager remain mounted as existing management views and are reached through the user menu's Admin submenu; this grouping is navigation, not a new authorization role.
- Tune Manager lists only published tunes; bundled local assets remain pipeline fixtures, not selectable catalogue entries.
- Shared dropdown submenus own mouse-exit dismissal and tag their portaled descendants so nested menus stay open during traversal while abandoned branches close; keyboard and touch behavior stays with Radix.
- Accounts own practice profiles (`local_users.auth_user_id`); per-player data stays keyed by `local_user_id` and is guarded by `owns_local_user()` in RLS and `_shared/auth.ts` in edge functions — reuses existing progress keys instead of re-keying every table.
- Admin rights come only from `user_roles`/`has_role()`; UI admin checks are display-only, while RLS and `requireAdmin` enforce them.
- Both iPad apps authenticate through the published HTTPS `/auth/native` bridge using independent `ASWebAuthenticationSession` implementations and Keychain stores. `ReplayWebURL` in each target's Info.plist is the configurable published origin; the bridge only hands off to the two fixed app callbacks with per-attempt state.
- Apple sign-in uses the managed Lovable OAuth helper on the shared web/native bridge and official Apple artwork with a monochrome Button variant — keeps provider credentials out of the app and preserves native return state.
- In-app tune builds (any signed-in user; non-admins publish account-only and cannot overwrite others' tunes; sources stored under `<user_id>/` in tune-sources): `tooling/tune_worker/` is a thin hosted wrapper (Modal) around the unchanged `tune_pipeline.build_tune` (`prepare` returns a compact note/measure view; `build` accepts an optional teacher plan). The `tune-build` edge function signs worker calls (HMAC), asks the TuneMaster prompt (copy of `tooling/tuneMaster.md`) via the AI gateway for the plan, falls back to the pipeline heuristic, and records `tune_build_jobs` — keeps build logic in the local pipeline and AI keys out of the worker.
- Hosted builder operations are documented in `tooling/tune_worker/README.md`. Git updates and Lovable publishing do not redeploy Modal; worker/pipeline changes need a separate deployment, and deployment success must not be reported as a verified in-app build without testing that path.
- Tune visibility: `tune_assets.is_global` (admin-set) or `owner_user_id` decides who sees a tune; uploads publish automatically as account-only via `tune-build` → `tune-publish`, and updates keep existing owner/visibility — avoids a separate publish step for uploads.
- Debug-mode tune taps open Tune Manager on that tune with the Overview as default view; ordering and duplicate detection live in the pure `src/utils/tuneOverview.ts` so they stay testable.
- MIDI export drops grace notes and NoteSequence conversion ends each note at the next same-pitch onset — music21 writes zero-length grace notes off-before-on, which otherwise leaves notes hanging for minutes.
- Student tune list order comes from per-account `tune_list_positions` (web and native read it; web appends missing tunes, uploads reserve the last slot before building) — keeps order stable across rebuilds and allows user reordering later.
- Upload progress lives on a building card in the tune list (`useActiveTuneBuilds`, with a client-side pending entry until the server job exists); the upload dialog only names the tune.
